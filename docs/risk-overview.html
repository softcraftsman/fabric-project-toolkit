AI-assisted Fabric development without sending PHI/PII to the model

An AI coding agent reads files, runs commands, and calls connected tools. Anything it reads can be sent to a model. This page explains where accidental exposure can occur, what the privacy guard plugin controls, and what remains open.

The balance in one view

The plugin trusts the curated project tree, reviews access to external files, and keeps the productive parts of the workflow.

Default denyUnknown tools, connectors, unlisted skills/agents and arbitrary shell commands are blocked on the CLI hook path
Root trustProject files need no entries or hashes. Only external files require individual human approval and matching SHA-256 digests
Synthetic diagnosticsReviewed synthetic tests can return bounded errors; other tasks default to status-only
9 Fabric agentsDelivery, architecture, pipeline, operations, semantic-model, quality and review roles remain available

How accidental exposure happens in a Fabric project

None of these steps requires bad intent: a helpful agent doing an ordinary task is enough.

Task startsDeveloper asks the agent to debug a pipeline or notebook.
Agent looks for evidenceIt opens data extracts, notebook outputs, logs or query results.
Content enters contextRows with PHI/PII become part of the prompt sent to the model.
Data leaves the boundaryThe model service is not covered by the BAA. This is a potential breach.

Data flow and where the protections sit

Business data lives in Fabric. The model service sits outside the BAA boundary. The guard sits on the local path between them.

Reading the diagram: the red connector path is separate from the amber export path. External files require individual approval and matching digests before reads or edits. Ordinary files inside the project, including Git definitions, need no approval entries or hashes. An export saved inside the project follows the allowed project-file path, even if it contains business data; keep such exports outside the trusted tree. Policy and plugin control paths remain protected. The guard does not screen pasted prompts, attachments, or VS Code context.

Quantifying the risk

No measured breach probability or risk-reduction percentage is available for project-root trust.

The earlier illustrative 46% score assumed per-file approval and digest checks throughout the project and does not apply to this policy. Project-local exports and later internal-file changes are now open exposure paths. A new assessment must account for project curation, external approvals, connector denials, and unmanaged context paths. Session and denial counts can inform a pilot assessment but do not by themselves measure breach probability.

What you keep, and what it costs

Still works
  • Reading, creating and editing project files without per-file registration or hashes
  • Project directory creation/discovery, searches, Git diff/log/status and project-scoped local history
  • Public Microsoft documentation, named Fabric skills/agents and reviewed synthetic-test diagnostics; no live business-row queries or requests for their output
  • Reading and editing individually approved external files while their digests match
  • Generating and reviewing code, notebooks and pipeline definitions
  • Running reviewed tests and builds, with pass/fail reporting
  • All nine Fabric solution-building agent roles for design and implementation
Deliberately limited
  • Only external files require individual approval and reapproval after changes
  • No live Fabric data queries; only 13 pinned documentation/inventory MCP tools, with server-side and hook restrictions
  • Test output is status-only unless a reviewed synthetic task explicitly enables bounded diagnostics
  • Workflows needing an exception require a separate reviewed extension
Positioning. This is a cooperative guardrail that lowers the likelihood of accidental disclosure by an agent. It is not a BAA compliance certification, a data-loss-prevention product, or an isolation boundary. Confirm model and service coverage under your agreement separately, and use administrator-managed policy where you need non-bypassable enforcement. Runtime behavior in a fresh Copilot CLI session should be verified with synthetic files before relying on it.

Fabric data engineering use cases and delivery impact

In a target project using the restrictive plugin, agents can author much of a solution but cannot independently deploy, run and validate it end to end.

These constraints describe projects consuming the plugin, not this infrastructure-only toolkit repository. Impact describes workflow friction, not a measured productivity percentage. Allowed operations still require normal client permissions.

The largest bottleneck is the feedback loop, not code generation. Agents can deliver architecture, implementation files, synthetic tests, deployment scripts and manual validation queries. Production correctness, performance, permissions and operational readiness remain unverified until authorized live steps are completed.

A greenfield solution with documented schemas supports workable assisted engineering. An existing, poorly documented Fabric environment is substantially more constrained. Narrow column-schema inspection and sanitized execution status are potential future improvements, not currently approved capabilities.

Connector verification and metadata limits. The restricted MCP tool exposure was protocol-tested, but actual Copilot plugin-server discovery and dispatch remain unverified. Inventory responses and service errors are not redacted; use only approved technical metadata and a least-privilege identity. Verify client and child-hook behavior with synthetic calls before relying on enforcement.
