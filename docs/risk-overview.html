Privacy-aware Fabric engineering

An AI coding agent reads files, runs commands, and calls connected tools. Anything it reads can be sent to a model. This page explains where accidental exposure can occur, what the privacy guard plugin controls, and what remains open. HIPAA-regulated health information under a BAA is one example, not a compliance claim.

Example: accidental exposure in a HIPAA-regulated Fabric project

None of these steps requires bad intent: a helpful agent doing an ordinary task is enough.

Task startsDeveloper asks the agent to debug a pipeline or notebook.
Agent looks for evidenceIt opens data extracts, notebook outputs, logs or query results.
Content enters contextRows with PHI/PII become part of the prompt sent to the model.
Data leaves the boundaryThe model service is not covered by the BAA. This is a potential breach.

Data flow and where the protections sit

In this illustrative healthcare scenario, business data lives in an approved Fabric environment while the selected model service is outside that BAA boundary. The guard sits on the local path between them; it does not verify actual coverage or routing.

Reading the diagram: the red data-query path is separate from the amber export path. The 13 reviewed documentation/inventory MCP tools are a narrow exception; their responses are not redacted. External files require individual approval and matching digests before reads or edits. Ordinary files inside the project, including Git definitions, need no approval entries or hashes. An export saved inside the project follows the allowed project-file path, even if it contains business data; keep such exports outside the trusted tree. Policy and plugin control paths remain protected for writes. The guard does not screen pasted prompts, attachments, or VS Code context. Osmos has no enabled live path.

Quantifying the risk

No measured breach probability or risk-reduction percentage is available for project-root trust.

No numeric reduction is claimed. Project-local exports and later internal-file changes are open exposure paths. An assessment must account for project curation, external approvals, connector denials, and unmanaged context paths. Session and denial counts can inform a pilot assessment but do not by themselves measure breach probability.

What you keep, and what it costs

Still works
  • Reading, creating and editing project files without per-file registration or hashes
  • Project directory creation/discovery, searches, Git diff/log/status and project-scoped local history
  • Public Microsoft documentation, named Fabric skills/agents and reviewed synthetic-test diagnostics; no live business-row queries or requests for their output
  • Reading and editing individually approved external files while their digests match
  • Generating and reviewing code, notebooks and pipeline definitions
  • Running reviewed tests and builds, with pass/fail reporting
  • All nine Fabric solution-building agent roles and six curated offline authoring, design, modeling, migration, integration and Osmos-planning skills
Deliberately limited
  • Only external files require individual approval and reapproval after changes
  • No live Fabric data queries; only 13 pinned documentation/inventory MCP tools, with server-side and hook restrictions
  • Test output is status-only unless a reviewed synthetic task explicitly enables bounded diagnostics
  • Workflows needing an exception require a separate reviewed extension

Positioning and scope

Positioning. This is a cooperative guardrail designed to reduce accidental disclosure by an agent; effectiveness has not been measured. It is not a BAA compliance certification, a data-loss-prevention product, or an isolation boundary. Confirm model and service coverage under your agreement separately, and use administrator-managed policy where you need non-bypassable enforcement. Runtime behavior in a fresh Copilot CLI session should be verified with synthetic files before relying on it.

In a target project using the restrictive plugin, agents can author much of a solution but cannot independently deploy, run and validate it end to end.

These constraints describe projects consuming the plugin, not this infrastructure-only toolkit repository. Impact describes workflow friction, not a measured productivity percentage. Allowed operations still require normal client permissions.

Curated Fabric expertise and the Osmos boundary

Reviewed Microsoft Fabric Skills guidance is adapted into six self-contained skills with pinned provenance and MIT attribution. Existing agents remain. Local code, definitions, migration assessments and synthetic tests are valid deliverables without live execution. Upstream MCP registrations, executable helpers and automatic updates are not imported.

Osmos is an opt-in Fabric-side analysis design, not enabled execution. The offline boundary validates consent bound to exact task scope and projects only fixed operational statuses, validated IDs and timestamps. Live dispatch always fails closed. Approval records are not a trusted human approval mechanism, and these tests do not establish service behavior.

Before any future capacity-consuming run, obtain explicit user approval with a warning about additional Fabric capacity usage. Changed scope needs new consent. Analysis, results, counts, assistant messages, raw errors and clarification exchanges stay in Fabric. A trusted adapter must prevent their return to GitHub Copilot before model exposure; remote prompt instructions alone are insufficient.

Live enablement requires verified service/authentication contracts, a trusted consent path and synthetic transport/error/logging checks. No live Osmos tasks were run. These privacy guardrails are not HIPAA certification, DLP, a sandbox, or assurance of model routing.

Validation status and deployment readiness

Content reviewed against the current local implementation on October 29, 2026. This describes the working tree, not proof that an installed or published plugin has these changes.

  • Synthetic regression suite: 68 tests ran; 67 passed and 1 was skipped because symlink creation was unavailable. Includes real PowerShell-hook invocations, packaging checks and offline Osmos boundary cases.
  • Page checks: all 11 section links, unique anchors, desktop sticky navigation, keyboard skip link, fixed light appearance regardless of system theme or URL theme parameters, 320/390/768-pixel layouts, table scrolling and print navigation were checked in headless Edge. Red is reserved for warning/caution content; ordinary headings and navigation use blue. No browser errors or external network requests were observed.
  • MCP protocol: the pinned server exposed exactly 13 reviewed tools; offline documentation worked and unexposed query/download/create calls were rejected. No customer data queries were executed.
  • Not established: actual Copilot plugin-server discovery/dispatch, runtime skill loading, child-hook inheritance, plugin coexistence, model routing, contractual coverage and live Osmos transport.
  • Required before use: review the target environment, update the installed plugin and guidance, and verify allowed/denied synthetic calls in a fresh client. Static preflight is not runtime enforcement evidence.
