AI-assisted Fabric development without sending PHI/PII to the model

An AI coding agent reads files, runs commands, and calls connected tools. Anything it reads can be sent to a model. This page explains where accidental exposure can occur, what the privacy guard plugin controls, and what remains open.

The balance in one view

The plugin narrows what an agent can touch to files a person has reviewed, and keeps the productive parts of the workflow.

Default denyUnknown tools, connectors, skills, delegation and arbitrary shell commands are blocked on the CLI hook path
Human-reviewedOnly individually classified source or synthetic files are readable, and only while their content digest still matches
Status onlyApproved tasks (for example tests) report pass/fail, not raw output, to the model
9 Fabric agentsDelivery, architecture, pipeline, operations, semantic-model, quality and review roles remain available

How accidental exposure happens in a Fabric project

None of these steps requires bad intent: a helpful agent doing an ordinary task is enough.

Task startsDeveloper asks the agent to debug a pipeline or notebook.
Agent looks for evidenceIt opens data extracts, notebook outputs, logs or query results.
Content enters contextRows with PHI/PII become part of the prompt sent to the model.
Data leaves the boundaryThe model service is not covered by the BAA. This is a potential breach.

Data flow and where the protections sit

Business data lives in Fabric. The model service sits outside the BAA boundary. The guard sits on the local path between them.

Reading the diagram: the red connector path is separate from the amber connection that combines the three data sources into the dotted local-export path. Exports are outside the guard until the agent tries to read the file, when unclassified reads are denied. Git item definitions follow a separate human-reviewed source-code route. The guard intercepts Copilot CLI tool calls, not Fabric itself; it does not screen pasted prompts or attachments, or govern VS Code Copilot. Dashed paths are outside its coverage.

Kept short on purpose. These need other controls; the plugin does not claim them.

How to read it
  • Likelihood: 1 rare, 3 plausible in normal work, 5 expected. Impact is 5 for any PHI/PII breach.
  • Score is likelihood times impact. The scenarios cover agent-driven paths. The guard removes most of the largest ones.
  • What remains is mostly human action and unmanaged client paths, which is where complementary controls matter.
Why this is not a breach percentage
  • The likelihood ratings are judgments, not measurements. Your team should adjust them for your environment.
  • A true probability needs incident and near-miss data. This baseline does not record how often the guard denies a call.
  • To get real numbers, count sessions and denied attempts over a pilot period and have security and compliance review them.

What you keep, and what it costs

Still works
  • Reading and editing reviewed source files
  • Generating and reviewing code, notebooks and pipeline definitions
  • Running reviewed tests and builds, with pass/fail reporting
  • All nine Fabric solution-building agent roles for design and implementation
Deliberately limited
  • Each file must be classified before the agent can read it
  • No live Fabric queries or connector tools in the baseline
  • Test failures are summarized, not streamed; detail is reviewed locally
  • Workflows needing an exception require a separate reviewed extension
Positioning. This is a cooperative guardrail that lowers the likelihood of accidental disclosure by an agent. It is not a BAA compliance certification, a data-loss-prevention product, or an isolation boundary. Confirm model and service coverage under your agreement separately, and use administrator-managed policy where you need non-bypassable enforcement. Runtime behavior in a fresh Copilot CLI session should be verified with synthetic files before relying on it.
